# Flathub: ngterm as a Flatpak

## Overview

- Split from `docs/plans/completed/20261105-release-signing.md` (user, 2026-11-07). This plan publishes ngterm on
  Flathub: a Flatpak built from source on the Flathub runtime, submitted to `flathub/flathub`, and kept current with
  each release.
- The work is mostly in the app, not the pipeline: a terminal inside the Flatpak sandbox must still run the user's
  host shell, so panes spawn on the host through `flatpak-spawn --host`.
- Built on the release plan: a release tag is what each Flathub update points at. It starts after that plan's first
  real release.
- Credentials are requested as their task lands, one step at a time, with anything secret asked through zenity
  dialogs; never through the chat.
- Parity: Flathub is a Linux channel, so it must work on any desktop (wlroots, KDE, GNOME, weston, X11), not only
  the dev box's compositor.

## Context (from discovery)

- The desktop app id is `com.nickalie.ngterm` (`packaging/linux/com.nickalie.ngterm.desktop`, `StartupWMClass`, the
  macOS bundle id). Flathub requires the id's domain to be verified (`nickalie.com`); otherwise the id becomes
  `io.github.nickalie.ngterm`, verified through GitHub.
- Panes spawn through `ngterm-pty` (openpty) and the live-session server (`ngterm-session`); `ngtermctl` and the
  session server use sockets under the runtime and state dirs.
- WPE WebKit (HTML overlays) is built from source for the release (`scripts/build-release-wpe.sh`) and bundled; its
  sandbox needs `bubblewrap` and `xdg-dbus-proxy` on the host. Inside Flatpak the WebKit sandbox needs the
  Flatpak-aware path.
- libghostty-vt is built with the pinned Zig (`build/pins.env`).

## Development Approach

- As the release plan's: regular testing approach, tests in the same task, all checks green before the next task,
  this file kept in sync with the work.
- Checks are sized to the change (AGENTS.md > Choosing checks); the sandbox work gets tests in `ngterm-pty` /
  `ngterm-session` where it can run outside Flatpak, and a local `flatpak-builder` build for the rest. Never touch the
  user's running ngterm: the Flatpak build runs headless or as a dev instance with its own socket and state dir.
