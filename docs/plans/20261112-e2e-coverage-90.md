# E2E code coverage to 90%, per app and platform

## Overview

The user (2026-11-12): "read the e2e survey and let's increase e2e coverage to 90%". The measure is the user's
choice: **e2e code coverage, measured like usual, fully automatic: no person involved, no hand-kept flow lists.**

**Target: at least 90% line coverage from the real-binary e2e runs, for each app on each platform, computed and gated
by CI with floors that only rise.**

| app | platforms | code measured (what its build compiles) | e2e runs that count |
|---|---|---|---|
| desktop | Linux, Windows, macOS | the staged `ngterm`, `ngtermctl`, `ngterm-session`, `ngterm-web` (Linux) | the conformance suite on the instrumented stage, every layer, plus its remote leg |
| headless | Linux, macOS | the staged `ngterm-headless`, `ngtermctl`, `ngterm-session` | `scripts/test-mobile-e2e.sh` and the other headless e2e in the same job, plus the conformance remote leg's headless origin |
| Android | the emulator (phone and tablet AVDs) | the app's Kotlin (`:app`, `:core`, generated UniFFI bindings out) and the Rust core (`libngterm_mobile.so`) | the instrumented tests on the emulator against a real headless machine |
| iOS | the simulator (phone and tablet) | the app's Swift (app target and local packages; test targets and the fake core out) and the Rust core | the UI tests on the simulator against a real headless machine |

Where it stands (the survey, main at `6cd9177c`, 2026-11-12): desktop Linux 60.85% (63,250/103,952 lines), Windows
60.93%; macOS not run; headless not instrumented (its crate is 0% in the desktop report); Android and iOS full stack
never run against a real machine and not measured. About 30,400 more Linux desktop lines must run to reach 90%.

The survey's flow tables (`.teamlead/e2e-survey-20261112.md` in the main checkout) are a map of where coverage is
missing, not the measure. Unit coverage stays as it is: separate, `cargo test` / Kover / the iOS Unit plan, its own
floors, 90% already the aim.

## Decisions

- **One measure: line coverage of real binaries driven from outside.** In-process tests (`ngterm-gpui/tests/*`
  window tests, Robolectric, XCUITest on the fake core, `cargo test`) never count toward it, even when they launch
  windows.
- **Per app and platform, over what that platform's build compiles.** The report reads only the coverage maps of the
  app's own binaries/modules built for that platform. Code cfg'd out for the platform is not in them. Each app has its
  own set of binaries, so `ngterm-headless` leaves the desktop number and becomes its own app.
- **One CI workflow owns each number.** The app/platform's e2e may run in several jobs (shards, phone and tablet).
  The workflow then merges their `lcov.info` in a final job and judges there. Numbers are never merged across
  workflows or commits.
  - desktop Linux and headless Linux: `linux.yml`;
  - desktop Windows: `cross-platform.yml`;
  - desktop macOS and headless macOS: `macos.yml` (settled by Task 6);
  - Android: `android.yml`;
  - iOS: `ios.yml`.
- **Every language reduces to lcov**, and one tool judges them all. That tool is `code_coverage.py` with its
  e2e/app mode, and `check_coverage.py`.
  - Rust comes through `llvm-cov export`, as today.
  - Kotlin comes from JaCoCo XML, converted.
  - Swift comes from `xccov` JSON, converted.
  - A mobile app's total is its Kotlin/Swift lines plus its Rust core's lines, summed.
- **Exclusions live in code, next to the code, with a reason.**
  - Mark a function with one comment form in all three languages: `// e2e-coverage: off: <reason>` on the line
    directly above the function (its attributes or annotations may sit between).
  - Mark a whole file with `// e2e-coverage: off-file: <reason>` as its first non-blank line.
  - The tool resolves a marker to the function the coverage data starts on the next line. A marker with no reason,
    or one that resolves to no function, fails the report (exit 2).
  - The report gives the excluded share: excluded lines / (measured + excluded), per app and per crate/module. It
    also lists every marker with its file, line and reason in the job summary.
  - A marker is for code that truly cannot run end to end: a platform callback no runner can trigger, a crash
    handler. Code an e2e test could reach gets the test. Code an app links but never calls (another app's path) is
    moved behind that app's crate or feature where that is small. Otherwise it is marked, and the reason names the
    app that runs it.
  - Unit coverage ignores these markers. AGENTS.md's rule against coverage exclusions stays for unit coverage.
- **Gates.**
  - Each app/platform has a floor file: one `total` line plus one line per crate (Rust) or module/target
    (Kotlin/Swift), in `conformance/coverage/e2e-floor-<app>-<platform>.txt`. The two existing desktop files move
    there.
  - A drop of more than the tolerance below a floor fails. Floors only rise, raised from a batch of at least two
    same-build runs, as today.
  - The summary always shows each total's distance to 90%.
  - When a total's floor reaches 90, `--min 90` joins that job's check, so it can never go back under 90. The last
    task turns `--min 90` on everywhere.
- **The noise gets fixed, not widened.** The 0.5 pt tolerance stays. Code whose execution varies between runs of
  one build gets a test that makes it run every time (Task 2).
- **Remote e2e runs over a real loopback sshd**, unprivileged, on 127.0.0.1, with a key the harness generates and a
  known_hosts it writes into the viewer's private home. The mobile e2e already proves this on CI. No network leaves
  the runner, and no test touches the user's ssh config.
- **Mobile full stack against a real headless:**
  - The CI job starts the same headless + sshd world `test-mobile-e2e.sh` builds (a `--serve` mode).
  - The emulator reaches it at 10.0.2.2, the simulator at 127.0.0.1.
  - The test authorizes a key the harness generated through the app's own Import key flow. First-run key creation
    stays the existing device test.
- **Research is its own early task** (Tasks 6-10). Its result is written into this plan, under the task, before the
  tasks that depend on it start.
- **Windows and macOS gate on CI.** The Windows VM and the Mac are for debugging only. A Windows or macOS change is
  proven on a `ci/<task>` branch run.
- **Strict lint from day one** for every new test module, under its language's existing strict gate: Rust tests
  under clippy `-D warnings`, Kotlin androidTest under the app's detekt, Swift UI tests under `mobile/ios`'s
  SwiftLint, shell under shellcheck. The conformance suite has no Python linter today; adding one to the whole suite
  is its own change, outside this plan.
- **No private values in tracked files**: hosts, IPs other than loopback and the emulator's 10.0.2.2, VM names,
  machine paths.

## Development Approach

- **Testing approach**: TDD where it applies.
  - Tool and harness code gets self-tests first (`conformance/selftests`, host-free).
  - Each e2e test asserts what a user, a client or the OS observes: tree, `session.text`, socket replies, files,
    pixels from the trace screenshot. Coverage is the result, never the assertion.
  - An app bug a new e2e test finds gets its Rust/Kotlin/Swift test first, then the fix.
- New conformance tests follow the reference discipline: green on reference-macos first, or, for what the reference
  cannot host, a Rust-only capability with `--must-pass` (conformance/README.md).
- Newly green ids go into the ratchet with `check_ratchet.py --add`. A ratchet id never goes red.
- Each raising task ends by raising its app's floors from two same-build CI runs (`check_coverage.py --add`).
- Gates follow AGENTS.md › Choosing checks: the touched crates, the self-tests, a partial suite run over the touched
  ids. The full suite is CI's.
- No dev instance, probe, `ngtermctl` call, sshd or emulator touches the user's running ngterm, display, session bus,
  ssh config or agent (AGENTS.md › Never touch the user's running ngterm).
- A task bigger than a day once its gap list is known gets split by the lead in this plan (➕ prefix), by module.

## Solution Overview

```
per app/platform CI workflow
  e2e jobs (shards, AVDs, simulators) on instrumented builds
    Rust: LLVM profiles (pooled per binary, flushed on every exit path) ─┐
    Kotlin: JaCoCo .ec from the device ──────────────────────────────────┼─ each job: lcov.info for its app
    Swift: .xcresult coverage ───────────────────────────────────────────┘
  final job: merge the jobs' lcov.info
    → code_coverage.py e2e --app <app> --platform <os>
        app = its binaries/modules; vendor/, -sys, generated bindings, test code out
        // e2e-coverage: off markers → excluded, listed, excluded share
        → summary.md (total, per crate/module, distance to 90, excluded share)
    → check_coverage.py --floor conformance/coverage/e2e-floor-<app>-<platform>.txt [--min 90]
```
