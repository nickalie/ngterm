# Spike: libghostty-vt terminal in a gpui-kit window

Plan: `docs/plans/20261014-gpui-frontend.md`, Task 1. Code: `spikes/gpui-term/` (outside the workspace; throwaway).
Run on 2026-10-14, Linux (CachyOS), headless weston 15.0.1 with Mesa's lavapipe (llvmpipe, Mesa 26.2.4) as the only
Vulkan driver. All numbers are from that software-rendered setup and are a sanity check, not a performance verdict.

Spike code and raw results: branch `spike/gpui-term` at commit `74d7394` (`spikes/gpui-term/`,
removed from `gpui-frontend` in Task 4).

## Verdict

**Pass.** A gpui-kit window draws a libghostty-vt terminal (backgrounds, shaped text, cursor, kitty image) fed by a
real PTY running `zmx attach` under a private `ZMX_DIR`; keys go through libghostty-vt's `KeyEncoder`, IME
preedit/commit through GPUI's input handler, wheel scroll moves the viewport, and resizing reaches both the VT and the
PTY. Every scripted check passes (`results/final-report.json`). Four findings change the plan (section "Changes for the
plan"): libghostty-vt types are `!Send`, the 0.2.2 wrapper pins a different Ghostty commit than the plan says and needs
**Zig 0.15.2**, several effects the plan relies on do not exist in 0.2.2, and GPUI needs a `wl_seat` (the suite's
weston must run with `--fake-seat`).

## What was built

- `src/term.rs` — the pane core. A libghostty-vt `Terminal` owned by a **dedicated terminal thread** with its
  `RenderState`, row/cell/placement iterators, key and mouse encoders; a PTY reader thread (`portable-pty`, 64 KiB reads)
  and a child-wait thread feed it through one `mpsc` channel. After each drained batch the terminal thread publishes a
  `Frame` in the spike's own types (rows of cells: text, fg, bg, style flags, wide/spacer; cursor; kitty placements with
  RGBA data shared by `(image id, generation)`) into `Arc<Mutex<Shared>>`, but only when the UI has asked for one
  (`FrameWanted` after each paint), so frame building runs at most once per painted frame. Clean rows are shared with the
  previous frame (`Arc<Row>`), from `RowIteration::dirty`. libghostty-vt types never leave the module.
- `src/main.rs` — gpui-kit app (`gpui_kit::application`, `init`, `open_window`): a `TermView` with a custom
  `TerminalElement`. Prepaint computes the grid from the font metrics (`advance('M')`, ascent + descent × 1.15), sends
  `Resize` on change, and re-shapes only rows whose `Arc<Row>` changed: one `shape_line` per run of equal style, with
  `force_width` = the cell width (2× for wide cells) so fallback glyphs stay on the grid. Paint: whole-area background,
  merged background quads per row, kitty images below text, text, images above text, cursor (block with the glyph
  redrawn in the background color, bar, underline, hollow when unfocused), IME preedit over the cursor cell.
  `window.handle_input(ElementInputHandler)` makes the view the IME target; `on_key_down` encodes keys; `on_scroll_wheel`
  scrolls.
- `src/control.rs` + `check.py` — a line-protocol control socket (`key`, `type`, `preedit`, `commit`, `scroll`,
  `resize`, `dump`, `quit`) running each command on the UI thread through the real GPUI paths
  (`Window::dispatch_keystroke`, `Window::dispatch_event(ScrollWheel)`, the view's `EntityInputHandler` methods,
  `Window::resize`), and the scripted checks: a private headless weston per check (`--renderer=gl`, Mesa EGL vendor,
  `--debug` for `weston-screenshooter`, `--fake-seat`), a fresh root under `/tmp` (runtime dir, HOME, `ZMX_DIR`), every
  child's environment built from scratch (no `AGTERM_*`, `ZMX_*`, `WAYLAND_DISPLAY`, `DISPLAY`), `VK_DRIVER_FILES` →
  lavapipe, zmx processes reaped only by their own `ZMX_DIR`.
- `cargo.sh` (Zig on PATH, `GHOSTTY_SOURCE_DIR`, the agents slice), `fetch-ghostty-src.sh` (the pinned Ghostty source),
  `run-check.sh`, `bench.sh`; `results/zmx_probe.py` and `results/debug_zmx.py` (the zmx first-paint investigation).

Run: `spikes/gpui-term/cargo.sh build --release && spikes/gpui-term/run-check.sh [--keep DIR]`;
`spikes/gpui-term/bench.sh 3 <GTK stage>` for the throughput table. The lavapipe ICD and an htop binary came from the
signed CachyOS packages `vulkan-swrast 26.2.4` and `htop 3.5.3` unpacked into `~/.cache/agterm-rs/vendor/` (not
installed system-wide; `LAVAPIPE_ICD`/`SPIKE_HTOP` override the paths).

### Throughput: `time cat` of a 50 MiB file

Same headless setup for both builds; GTK = the main checkout's `target/conformance-stage` (staged 2026-10-14 17:10)
through the conformance adapter, its pane behind the same zmx binary. 53 085 294 bytes reach the VT (50 MiB plus the
PTY's CR for each LF). `cpu` is the app process's user + system time over the run.

| build | `cat` seconds (3 runs) | app CPU seconds |
|---|---|---|
| GTK (libghostty, GL) via zmx | 0.41 / 0.47 / 0.51 | 0.89 / 0.94 / 1.08 |
| spike via zmx | 1.45 / 1.49 / 1.55 (final run 1.38) | 1.13 / 1.15 / 1.29 |
| spike, plain shell (no zmx) | 0.56 / 0.64 / 0.86 (final run 0.52) | 1.10 / 1.28 / 1.70 |

Inside the spike's terminal thread the 53 MB cost 0.27–0.42 s of `vt_write` (≈130–195 MB/s) and 0.02–0.05 s of frame
building (≈0.6 ms per frame for 141×41 cells, 35–95 frames per run). So the terminal thread is mostly idle: neither
parsing nor snapshotting is the bottleneck. On a plain shell the spike is within 1.0–1.7× of the GTK build; behind
zmx it is ~3× slower although the same zmx feeds both, which points at the read path between zmx's client and the PTY
(read sizes, per-read channel messages and wakes) — to profile in Task 9, not a blocker.

## Versions and build facts (for Task 5 and the plan)

- **gpui-kit 0.7.3** pins **gpui-pre `=0.3.9`**, "gpui-pre snapshot of zed@93d7456" (crate description); with it
  gpui-pre-platform/-linux 0.3.9 (features `font-kit`, `x11`, `wayland`, `runtime_shaders`) and **wgpu 29.0.4**.
- `gpui-fast` is an opt-in feature of gpui-kit, off by default. The spike builds with `default-features = false`, and
  `cargo check --features kit-defaults` (gpui-kit's defaults `component` + `assets`, i.e. the plan's "defaults minus
  gpui-fast") builds too; no `gpui-fast*` package is in `Cargo.lock` either way.
- **libghostty-vt / libghostty-vt-sys 0.2.2** pin Ghostty **`a887df42c56f6de86c0fe6da9c4eeca37931e083`**
  (`GHOSTTY_COMMIT` in `libghostty-vt-sys/build.rs`), not `3425025e…` as the plan's Context says.
- Ghostty at that commit declares `minimum_zig_version = "0.15.2"` and **does not build with Zig 0.16**
  (`build.zig: member function expected 4 argument(s)`); the spike builds with Zig 0.15.2.
- How `build.rs` finds things: Zig is `Command::new("zig")` — **PATH only, no env override**. With a version manager's
  cargo shim first on PATH, the build runs its `zig` shim (which fails without a configured version), so `cargo.sh` calls
  rustup's `~/.cargo/bin/cargo` with a Zig 0.15.2 directory first on PATH. `GHOSTTY_SOURCE_DIR` replaces the git
  clone (a directory with `build.zig`); `GHOSTTY_ZIG_SYSTEM_DIR` adds `zig build --system <dir>` with a global cache in
  `OUT_DIR` (offline packages); without it Zig uses the default global cache (`~/.cache/zig`, which held every package
  here). Optimize mode follows the cargo profile (`Debug` for dev builds, `ReleaseFast` for release;
  `LIBGHOSTTY_VT_SYS_OPTIMIZE` overrides), CPU `baseline` (`LIBGHOSTTY_VT_SYS_CPU`), static `libghostty-vt.a` by default
  (feature `link-dynamic` otherwise). The Ghostty source archive is fetched by `fetch-ghostty-src.sh` from GitHub's
  archive endpoint, which does not resume: whole downloads are retried.

## Changes for the plan

1. **Thread model.** Every libghostty-vt type is `!Send` and `!Sync` (crate docs: the C API may use thread-local
   state), so "the IO thread calls `vt_write` under the pane's mutex; painting locks only for `begin_update`" cannot be
   written with the safe crate. What works (and what the crate docs recommend) is an **actor per pane**: one thread owns
   the `Terminal`, `RenderState`, encoders and selection state; the UI sends it input (keys are encoded there, since the
   encoder reads terminal modes) and gets frames in our own types. Snapshotting at most once per painted frame keeps it
   cheap (0.6 ms per full 141×41 frame). The PNG decoder for kitty images is **thread-local** too
   (`set_png_decoder`): it must be installed on each terminal thread. Affects Solution Overview > Threads and Task 9.
2. **Effects missing in 0.2.2.** The wrapper has `on_pty_write`, `on_bell`, `on_enquiry`, `on_xtversion`,
   `on_title_changed`, `on_pwd_changed`, `on_size`, `on_color_scheme`, `on_device_attributes`, `on_clipboard_write`.
   It has **no** desktop notification (OSC 9/777), progress report (OSC 9;4), clipboard read (OSC 52 reads are always
   dropped), mouse shape (OSC 22), or color-change notification, and **no `search` and no `snapshot` module** (the C
   API has no search either). The plan's Context lists `on_desktop_notification`, `on_progress_report`,
   `on_clipboard_read`, `search` and `snapshot` as present. The C API's standalone OSC parser (`ghostty_osc_*`) knows
   these commands, so the fallbacks are an upstream PR (exposing them as effects, the C side already parses them) or
   scanning the PTY stream ourselves. Search can be built on the formatter / grid refs in the meantime.
3. **Zig and the pin.** `LIBGHOSTTY_VT_REV` = `a887df42…` at 0.2.2 and its own Zig pin **0.15.2** (not 0.16): Task 5
   needs a separate Zig pin for libghostty-vt next to `GHOSTTY_ZIG_VERSION`/`ZMX_ZIG_VERSION` (both 0.16.0), a Zig 0.15.2
   reaching the build script through PATH (a PATH wrapper or `[env] PATH` — there is no variable), and a fix for a
   version-manager cargo putting its `zig` shim first.
4. **Headless harness.** GPUI panics on a compositor without `wl_seat` ("Wayland compositor does not provide wl_seat");
   weston's headless backend has none unless started with **`--fake-seat`**. Task 17 adds it, next to lavapipe
   (`VK_DRIVER_FILES`), which is not installed on this machine: the spike used the signed `vulkan-swrast` package
   unpacked into the vendor dir, so Task 17 needs a way to provide it (a documented package, or the same unpack).

## Surprises

- **zmx first paint.** `zmx attach` shows nothing until it sees a real size change after its attach handshake: when
  the shell prints its prompt between the client's attach and its first snapshot, the daemon holds the prompt
  (`zmx screen` shows it) while the attached client never sends it. A resize that lands before the handshake is lost, and
  two quick resizes inside one SIGWINCH look like no change. The spike holds a one-row-smaller size for 50 ms and
  restores it when the client first speaks, then again at 0.1/0.3/0.8/1.5 s until the session has sent more than its
  ~32-byte greeting; 12/12 launches and the full suite pass with it, while without it 1 to 4 of every 6 launches
  stayed blank. The GTK build does not show it in the suite, presumably because libghostty resizes the surface after
  the child starts (not verified). For Task 11 (launch): either the same
  nudge, or fix the race in the zmx patch.
- `RustPngDecoder` (feature `png`) cannot be used: it has no public constructor (its doc example calls a `new()` that
  does not exist) and decodes into an empty buffer. The spike decodes with the `png` crate itself.
- `ghostling_rs` on the wrapper's master already uses a newer API than 0.2.2 (`Terminal::new(cols, rows)`,
  `mouse_shape()`): read 0.2.2's own docs, not the example.
- GPUI's `RenderImage` holds BGRA; kitty RGBA data needs a channel swap (done once per image generation).
- `Window::dispatch_keystroke` runs the same path as a real key (key-down listeners, then the input handler with
  `key_char`), so key-level tests can drive the real element without a seat.

## API gaps in libghostty-vt 0.2.2 (candidates for upstream PRs)

- effects for OSC 9/777 notifications, OSC 9;4 progress, OSC 52 read, OSC 22 mouse shape, OSC 4/10/11/12 color
  changes (for the chrome tint);
- a search API (or the C API's) and the `snapshot` the plan expected;
- `RustPngDecoder` constructor and buffer fix;
- a `Send` story: an owned, `Send` terminal handle the C API guarantees thread-agnostic, or documented rules for moving
  a terminal between threads, would allow the plan's original IO-thread design;
- a Zig-path override in `libghostty-vt-sys`'s `build.rs` (e.g. `ZIG`), so a toolchain manager's shim does not win.
